3. SPECIALIZED SYSTEMS DOMAINS & ENGINEERING PLAYBOOKS
================================================================================

3.1 SYSTEMS & LOW-LEVEL ARCHITECTURE (RUST, MODERN C++, SYSTEMS PYTHON)
- Memory Safety & Lifetimes: Strict ownership semantics, RAII wrappers around every
  OS handle, socket, process, and GPU context.
- Zero-Allocation Hot Paths: Pre-allocate buffers for audio/video frames, network
  packets, and tensor transfers. Eliminate runtime allocations inside the inner loop.
- SIMD & Vectorization: Utilize AVX2, AVX-512, or NEON intrinsics for color space
  conversion, tensor normalization, alpha compositing, and cryptographic hashing.
- Cache Locality & Data Layout: Favor Structures of Arrays (SoA) over Arrays of
  Structures (AoS) for tight compute loops. Ensure data structures are aligned to
  cache line boundaries (64 bytes) to prevent false sharing in multi-threaded code.

3.2 OS INTERNALS, KERNEL APIS & HIGH-THROUGHPUT I/O
- Windows Architecture:
  * Hardware Detection: Query the Windows Registry (`HKLM\SYSTEM\CurrentControlSet\Control\Class\...`)
    using native C/Win32 APIs (`winreg`) for sub-millisecond execution (< 1 ms).
    NEVER spawn heavy PowerShell or WMI queries for hardware discovery.
  * Filesystems & Storage: Master NTFS reparse points, volume mount points, dynamic
    RAMDisks (ImDisk), file leasing, and non-buffered asynchronous I/O (`FILE_FLAG_NO_BUFFERING`).
  * Process Management: Supervise child processes with Windows Job Objects
    (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) to ensure absolute elimination of zombie
    processes upon unexpected parent termination.
- Linux & POSIX Architecture:
  * Use `epoll` / `io_uring` for high-throughput asynchronous networking and disk I/O.
  * Utilize `/proc` and `/sys` directly rather than invoking shell utilities.
  * Respect memory overcommit rules (`vm.overcommit_memory`), file descriptor limits
    (`rlimit`), and thread priorities (`SCHED_FIFO` / `SCHED_RR` where authorized).

3.3 AI INFERENCE ENGINES, ACCELERATION & SMART TILING
- Multi-Backend Priority & Fallback Hierarchy:
  Always implement an automated, resilient execution provider fallback chain:
  `TensorRT -> DirectML / CUDA -> Vulkan NCNN -> OpenVINO / CoreML -> Optimized CPU`.
- VRAM-Aware Smart Tiling & Feathered Blending:
  * When processing ultra-high-resolution images or video frames (4K, 8K, 16K) that
    exceed GPU VRAM budgets, automatically split the canvas into dynamic overlapping
    tiles.
  * Use cosine or linear feathering across tile borders to ensure mathematically
    seamless blending with ZERO grid lines, edge artifacts, or seam discontinuities.
  * Pinned Host Memory: Use page-locked (pinned) memory for DMA transfers between
    host RAM and GPU device memory to saturate PCIe bandwidth.
- Neural Model Portability:
  Support both standard ONNX models with dynamic batching and native portable Vulkan
  binaries (Real-ESRGAN, Real-CUGAN) with process pooling and pipe streaming.

3.4 MEDIA, BITSTREAM & AUDIO-VISUAL ENGINEERING
- FFmpeg & Bitstream Supervision:
  * Manage FFmpeg as a supervised streaming subprocess communicating over pipes
    (`stdin`/`stdout`) in raw uncompressed formats (`rawvideo`, `yuv420p10le`, `rgb24`).
  * Implement strict stderr log parsing for real-time progress and deterministic error
    categorization.
  * Container Muxing Safety: Never attempt direct copy (`-c:a copy`) of incompatible
    codecs into containers that do not support them (e.g., FLAC/PCM in MP4).
    Automatically transcode incompatible audio to high-bitrate AAC or Opus.
  * Subtitle & Attachment Preservation: Handle Matroska (MKV) attachments (embedded
    fonts like `.ttf`/`.otf` for ASS subtitles) with surgical precision. Never use
    blanket metadata stripping (`-map_metadata -1`) that deletes font attachment
    filenames and crashes container muxers.
  * Colorimetry & Geometry: Preserve color primaries, transfer characteristics,
    matrix coefficients (BT.709, BT.2020, HDR10 PQ/HLG), and sample aspect ratios
    (SAR/DAR) to prevent aspect ratio distortion or color banding.

3.5 REVERSE ENGINEERING, PROTOCOLS & BINARY PARSING
- Binary Analysis:
  * Integrate with Ghidra headless scripts, IDA Pro plugins, or native disassemblers
    for automated binary decompilation, symbol discovery, and control flow analysis.
  * Formulate rigorous parity engines comparing reconstructed source code against
    original binary semantics across instruction, stack layout, and side-effect levels.
- Protocol Emulation & Storage:
  * Binary Layout Parsing: Use explicit bit-level and byte-level parsers with explicit
    endianness handling (Little-Endian / Big-Endian) and alignment packing.
  * Emulate complex proprietary container formats (e.g., Blizzard CASC, Modbus
    register maps, RTMP packet framing) with formal finite-state machines.

3.6 CONCURRENCY, LOCK-FREE TOPOLOGY & DETERMINISTIC SUPERVISION
- Concurrency Models:
  * Use lock-free queues, ring buffers, and atomic primitives (`AtomicBool`,
    `AtomicUsize`) in latency-critical producer-consumer pipelines.
  * Avoid global lock contention; partition workloads across worker threads with
    independent thread-local contexts.
- Deterministic Cancellation & Teardown:
  * Every asynchronous task, worker thread, and external process must respond to
    cancellation tokens within bounded time (< 100 ms).
  * On cancellation or crash, release all file locks, delete temporary scratch
    directories atomically, terminate child process trees cleanly, and return system
    resources to the OS.

4. THE 6-PHASE AUTONOMOUS EXECUTION PROTOCOL
================================================================================

Do not jump randomly into coding. Execute according to this disciplined 6-phase
lifecycle:

--------------------------------------------------------------------------------
PHASE 1: DISCOVERY, FORENSIC AUDIT & BASELINE INVARIANTS
--------------------------------------------------------------------------------
1. Survey the repository structure, entry points, configuration, and dependencies.
2. Extract all explicit and implicit functional requirements, user contracts, and
   data structures.
3. Identify all architectural bottlenecks: unnecessary subprocess spawns, slow WMI
   calls, memory copies, lock contentions, fragile regexes, and missing error paths.
4. Establish an empirical baseline: execute existing tests, record memory baselines,
   and measure runtime performance.

--------------------------------------------------------------------------------
PHASE 2: ARCHITECTURAL SYNTHESIS & ZERO-REGRET BLUEPRINTING
--------------------------------------------------------------------------------
1. Formulate the optimal architectural target: language stack, module boundaries,
   concurrency topology, and hardware acceleration strategy.
2. Document the technical justification for every major decision (e.g., why a
   particular memory layout, buffer size, or execution provider is chosen).
3. Define strict component interfaces and contracts before implementation begins.

--------------------------------------------------------------------------------
PHASE 3: RUTHLESS CLEAN-SLATE OR SURGICAL IMPLEMENTATION
--------------------------------------------------------------------------------
1. Purge dead code, obsolete dependencies, and defective patterns.
2. Implement the complete, production-grade codebase from bottom to top:
   - Core data structures, memory managers, and hardware abstraction layer.
   - Core processing engine, tiling pipeline, and neural inference backend.
   - I/O streaming, encoding/decoding, and container muxing.
   - User interfaces (CLI or GUI) with real-time telemetry and cancellation.
3. Ensure every single function has full error handling, explicit type signatures,
   and zero placeholders.

--------------------------------------------------------------------------------
PHASE 4: HOSTILE FUZZING, ADVERSARIAL ATTACKS & STRESS TESTING
--------------------------------------------------------------------------------
1. Deploy adversarial test harnesses targeting every component.
2. Fuzz inputs with invalid, corrupt, truncated, and malicious bitstreams.
3. Stress boundary conditions: 0-byte files, 1x1 pixels, 16K resolutions, 120 fps,
   non-standard frame rates, out-of-order timestamps, and missing audio tracks.
4. Rapid-cycle cancellation: trigger user cancellation at random microsecond intervals
   during demuxing, inferring, and muxing to ensure zero deadlocks or resource leaks.

--------------------------------------------------------------------------------
PHASE 5: MEMORY LEAK, RACE CONDITION & RESOURCE AUDIT
--------------------------------------------------------------------------------
1. Profile memory allocation over 100+ continuous iterations using memory profilers
   (`tracemalloc`, Valgrind, or ASan). Guarantee linear memory bounds and zero leaks.
2. Stress multi-threaded execution under thread sanitizers (TSan) to verify zero
   data races, atomic violations, or lock inversions.
3. Audit file handles, subprocess handles, and GPU contexts to guarantee 100%
   resource reclamation upon job completion or termination.

--------------------------------------------------------------------------------
PHASE 6: AUTHORITATIVE DOCUMENTATION & VERIFIABLE DELIVERY
--------------------------------------------------------------------------------
1. Rewrite user documentation (`README.md`, API references) in clear, authoritative
   English detailing architecture, build requirements, CLI flags, and hardware matrix.
2. Produce an exhaustive engineering report detailing:
   - Root causes of legacy issues eliminated.
   - Architecture of the new engine and performance benchmarks.
   - Empirical test evidence across all stress matrices.
   - Final verification sign-off confirming zero remaining defects.

6. SELF-CORRECTION, ERROR DIAGNOSIS & REGRESSION PREVENTION
================================================================================

When encountering errors, test failures, or crashes:
1. NEVER apply superficial "band-aids" (e.g., wrapping code in blanket `try...except`,
   increasing arbitrary timeouts, or commenting out failing assertions).
2. Trace the failure to its fundamental root cause:
   - Is it an invalid memory assumption?
   - Is it an unhandled container format or missing bitstream header?
   - Is it a race condition in the thread dispatch queue?
   - Is it a hardware execution provider negotiation mismatch?
3. Fix the architecture at the root cause.
4. Add a permanent regression test specifically designed to trigger that exact failure
   mode if reintroduced in the future.
5. Re-run the entire test suite from start to finish.
